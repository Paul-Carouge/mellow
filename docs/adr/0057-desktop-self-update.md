# 0057. The desktop app updates itself from the signed release packages

- Status: Accepted (wave 9 of the desktop client, ROADMAP M3 step 9)
- Date: 2026-11-13
- Builds on: [ADR-0003](0003-self-update-with-signed-releases.md) and [ADR-0016](0016-sign-releases-in-a-protected-ci-environment.md) (signed releases, the minisign key), [ADR-0018](0018-roll-back-the-executable-only-and-guard-the-install-location.md) (rollback), [ADR-0055](0055-desktop-release-packages-and-macos-signing.md) (the desktop packages and the stable macOS certificate)

## Context
ADR-0055 publishes the desktop app as a universal macOS zip and one Linux tarball per FFmpeg major version, each with a minisign signature whose trusted comment is the asset's name, signed with the same key as the server. Without a self-update, users install every release by hand, so most would run old versions, security fixes included. The server already updates itself (`mellow-server update`, crate `mellow-update`): it reads GitHub's latest release, downloads with size limits and timeouts, refuses a signature that does not cover the expected file name, and compares versions. The desktop differs in three ways: it is a graphical app a user keeps open, possibly in a voice call; on macOS it is a bundle whose code signature decides which privacy permissions macOS keeps; and on Linux its package depends on the system's FFmpeg major.

## Decision
- **One verification path**: the desktop uses `mellow-update` (`UpdateClient`, `Release`, `download_verified_asset`, `verify_signed_file`); the crate gained only a generic `download_verified_asset` (the server's `download_verified_executable` now calls it, unchanged in behaviour) and, behind a test-only feature, a client of a local release host. Same key, same GitHub endpoint, `https` only, no Mellow token or instance address in any request, no version in the user agent, at most 512 MiB per package held in memory, the signature checked before anything is written to disk.
- **When**: a first check one to six minutes after the start, then every 24 to 26 hours (random jitter), while the app runs. A check that falls during a voice call waits 15 minutes, as the download would take the call's bandwidth. A switch in Settings, About ("Automatic updates", on by default, kept in the preferences file) turns the scheduled checks off; "Check for updates" there always works.
- **Which copy may update itself**:
  - macOS: only a `Mellow.app` whose designated requirement names the bundle identifier `org.mellow.desktop` and a certificate (`certificate leaf = H"…"`), which is what the release signing produces. An ad hoc or locally built copy, or an executable outside a bundle, says it cannot update itself and never reaches the network.
  - Linux: only the copy `install.sh` puts at `~/.local/bin/mellow`. A binary under `/usr`, `/opt`, `/nix`, `/snap`, `/app` or `/gnu` belongs to a package manager and the app says to update it there; anywhere else (built from source, copied by hand) it says to use the package's `install.sh`. The folder must be writable, tested by creating a file in it, not by reading modes.
  - Both: the check of writability (macOS: the bundle's folder) happens before any download, so a copy that cannot be replaced never fetches a package. macOS: an app run from its App Translocation copy (opened where it was downloaded) says to move it to Applications.
  - Windows: compiled, and says "not supported yet" until Windows has a package (ADR-0055).
- **Which package on Linux**: the FFmpeg majors found as `libavcodec.so.N+54` in the usual library folders (`/usr/lib`, `/usr/lib64`, `/usr/lib/x86_64-linux-gnu`, `/lib/x86_64-linux-gnu`, `/lib64`, `/usr/local/lib`), newest first, the first the release carries. The system's libraries decide, not the running binary, so an app updated after a distribution upgrade gets the package that will start.
- **Staging**: the verified package is written into a fresh private directory (mode 0700, prefix `.mellow-update-`): beside the bundle on macOS, so the swap is a rename on one file system; in `<user cache>/mellow/updates` on Linux, not the temporary folder, which is often a tmpfs that `systemd-tmpfiles` empties after ten days while the app may still be open. macOS unpacks with `ditto -x -k` and then requires `codesign --verify --deep --strict -R=<the running app's designated requirement>` to pass on the new bundle, so an update keeps the same certificate and with it the camera, microphone, Screen Recording and keychain access (ADR-0055). Linux unpacks with `tar` and requires the package's folder, `install.sh` and `bin/mellow`. Leftover staging directories are removed once at each start, automatic updates on or off; each directory holds a `lock` file the staging process keeps locked, so a second running instance leaves it alone. While an update waits, the daily check goes on, and a newer release replaces the waiting one quietly.
- **Applying**, never during a call, and never over a copy reinstalled by hand since the update was staged (the installed file's device and inode are compared; a manual reinstall may be newer):
  - "Restart to update" (Settings, About, and a discreet button beside the user card's gear, disabled during a call with "Leave the call to restart and update.") swaps the update in and restarts the app through GPUI's restart, which waits for this process to end. A call joined while the update was being swapped in holds the restart until the call ends.
  - Otherwise the update is swapped in when the app quits, so the next launch runs it. The call ends with the quit anyway.
  - macOS: the new bundle and the installed one are exchanged in one atomic `renamex_np(RENAME_SWAP)` on APFS; elsewhere the installed bundle is renamed into the staging directory and the new one renamed into its place, the first undone if the second fails. If even that undo fails, the staging directory, which then holds the only copy of the app, is kept. The replaced bundle stays until the process exits (it still runs from it) and is removed at the next start.
  - Linux: the new package's own `install.sh` (covered by the signature) installs it, as a manual update would: it refuses with the missing library names when `ldd` finds one, renames the binary into place and refreshes the desktop entry and icons. The running binary is kept under a hard link meanwhile and renamed back if the script fails.
- **Interface**: Settings, About shows the version, where the update stands (read out politely), a problem in plain words (read out at once), the button and the switch, in English and French. Logs hold the problem's kind only, never paths (which hold the user's name).

## Consequences
- Users of the release packages get new versions within a day, and macOS keeps their permissions across updates. Copies from a package manager, from source or from elsewhere keep updating their own way.
- Trust is the server's: the minisign key in the binary and the trusted comment naming the asset. On macOS the certificate check adds a second, independent key: a stolen minisign key alone cannot replace the app. On Linux the signature is the only check, as for the server.
- A compromised release host can hold back an update (ADR-0016's freeze attack) but cannot make the app install an older or another platform's package.
- The quit path blocks the closing app for a rename (macOS) or `install.sh` (Linux, a copy of the binary and two cache refreshes): accepted, as no window is left to freeze.
- An update that installs but then fails to start is not rolled back automatically; the user reinstalls by hand. With the app kept in the background (ADR-0056), a ready update waits for a real quit or "Restart to update", possibly for days. A copy installed by an administrator into `/Applications` cannot be updated by a non-administrator account, and says so.
- An app killed before quitting drops its staged update; the next check downloads it again.
- A rotation of the macOS certificate (ADR-0055) is refused by every installed app ("not signed with the same certificate"): that release's notes must ask macOS users to install it by hand, which they must do anyway to see Gatekeeper's block and grant the permissions again.

## Alternatives
- **Sparkle (macOS) or a Flatpak / AppImage updater**: one more framework and format per platform, with its own key (Sparkle's EdDSA) beside ours; rejected for one Rust path shared with the server.
- **Apply at the next launch instead of at quit**: one more start-up step (and a second start) before the window shows; the quit path gives the same result without delaying the start.
- **Replace the files ourselves on Linux instead of running `install.sh`**: two copies of the install logic to keep in step; the script is signed with the package and already checks the libraries.
- **Pick the FFmpeg package from the running binary's own libavcodec**: wrong exactly when it matters, after a distribution upgrade to a new FFmpeg major.
