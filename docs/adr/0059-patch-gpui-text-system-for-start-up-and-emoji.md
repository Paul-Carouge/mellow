# 0059. Patch GPUI's Linux text system: system fonts after the first frame, colour emoji first

- Status: Accepted
- Date: 2026-11-14
- Builds on: [ADR-0051](0051-gpui-desktop-client.md) (GPUI from the `gpui-pre` snapshots, pinned with `=`), and follows the vendoring of `str0m` in [ADR-0052](0052-h264-next-to-vp8-in-the-voice-sfu.md)

## Context
Two faults of the Linux text system of `gpui-pre-wgpu` 0.3.11 (`CosmicTextSystem`, on cosmic-text 0.19), found by the desktop performance audit (`docs/desktop-performance-audit.md`, lot 1) and the message parity work:

- **Start-up waits for every system font.** `gpui-pre-linux` builds the text system with `CosmicTextSystem::new`, whose `FontSystem::new()` reads all installed fonts on the main thread before the first window can open: 8 to 20 ms when the files are in the page cache, 380 to 610 ms when they are not (first launch after login, memory pressure; 1 102 font files on the test machine). Mellow draws its interface with the fonts it embeds (Figtree, Source Code Pro, `theme/fonts.rs`) and needs system fonts only as fallbacks (emoji, other scripts).
- **Emoji come out in black and white.** For a character the font lacks, cosmic-text tries `DejaVu Sans`, `Noto Sans Symbols`… before `Noto Color Emoji`, so 😀 draws as a monochrome outline. A font's own fallback chain (`Font::fallbacks`, tried first) would fix it, but `load_family` drops every face without an "m" glyph, which rules out every emoji font. The messages branch worked around it by asking for weight 600 on emoji graphemes, which the composer's input cannot do.

Neither can be fixed from Mellow: both are inside the crate. Upstream (Zed's `crates/gpui_wgpu`, published weekly by Longbridge as `gpui-pre-wgpu`) has neither fix.

## Decision
- **Vendor `gpui-pre-wgpu` 0.3.11** in `vendor/gpui-pre-wgpu`, used through `[patch.crates-io]` and excluded from the workspace, as `vendor/str0m` is: the crate as published on crates.io (Apache-2.0, `LICENSE-APACHE` kept), without its benches; its unit tests read fonts from Zed's repository and are not run. Every change is marked `Mellow patch (ADR-0059)` and the manifest's header says what changed. `gpui-pre-linux` is not vendored: its call to `CosmicTextSystem::new` stays, and `new` changes behaviour.
- **System fonts on a background thread.** `CosmicTextSystem::new` starts with an empty font database and reads the system fonts (`FontSystem::new()`) on a thread named `system-fonts`. Until they are read, text is shaped with the fonts the app added; a glyph no font has is left out rather than drawn as a box. Once read, they join at the next `add_fonts`, `font_id` or `layout_line`: the app's faces move after the system's, as if added after them (the original order). Every `FontId` given out stays valid (GPUI's glyph atlas and metrics caches are keyed by it), but later lookups give new ones: GPUI also keeps per-`FontId` caches built without the system fonts (the line wrapper's character widths, measured on a missing glyph), and new ids leave them behind, with fallback chains resolved anew. `font_id` waits for the system fonts when no added font has the family asked for, so a system family still resolves rather than failing; `prewarm_fonts` waits for them; `all_font_names` lists what is known without waiting.
- **Mellow redraws once they are in** (`theme::redraw_with_system_fonts_once_read`, Linux): a background task calls `prewarm_fonts`, then the main thread calls `TextSystem::add_fonts` with no font, which drops GPUI's font lookups (so the next ones give the new `FontId`s) and line layouts (the patched `add_fonts` itself does nothing for no font), and refreshes the windows, so a line shaped before (an emoji left out) is shaped again.
- **Emoji fonts in a fallback chain.** A fallback family whose faces all lack "m" is still taken, through its first face. The "m" rule stays for primary fonts, where GPUI measures with it. An emoji font in a chain draws only graphemes shown as emoji (emoji presentation, U+FE0F, a keycap or a flag, not U+FE0E; `icu_properties`, already in the tree), so ☺ or ✔ alone keep a text font as in browsers; it draws them before the primary font, since a keycap starts with a digit and ©️ with a sign Figtree has; and it is asked at its own weight, since cosmic-text skips a face at another weight than the one asked (bold text fell back to a monochrome font). Mellow's interface font names `Noto Color Emoji` as its fallback on Linux (`theme::interface_font`, on the main window's root, so every text below it, the composer's input included, inherits it); macOS and Windows find their colour emoji font by themselves and are unchanged.

## Consequences
- Measured on release builds, launch to the main window's first render, median of 5 interleaved launches each, in headless gamescope on X11 (font files evicted with `posix_fadvise(DONTNEED)` for "cold"): cold 387 ms before, 45 ms after (`gpui_platform::application()` 341 ms, now 0.5 ms); warm 52 ms before, 46 ms after (8.4 ms, now 0.5 ms). Under load (load average 10): cold 681 ms before, 127 ms after. The system fonts join 340 to 650 ms after launch when cold, 1 to 2 ms after the first render when warm; the redraw that follows costs one frame.
- An emoji in the first frames of a cold launch appears a moment later instead of in black and white; nothing is drawn as a box meanwhile.
- `gpui-component`'s theme lists the installed fonts once per process, during `gpui_component::init`, before any font is added: it now finds none, keeps `.SystemUIFont` as its UI font, and logs once that `DejaVu Sans Mono` is not installed. Mellow draws its text in its own fonts, so nothing visible changes; a `gpui-component` element drawn in the theme's font before the system fonts are read waits for them (`font_id`).
- A colour glyph ignores the text's colour, so a hidden spoiler drawn in the bar's colour shows its emoji; some (😂) already did before this decision, through cosmic-text's own fallback. The message text paints the bar over the emoji of hidden spoilers (`RichText::covered_emoji`, from #351).
- One more vendored crate to carry. **Updating GPUI**: when `gpui-pre` moves past 0.3.11, check whether upstream fixed both faults; if not, copy the new `gpui-pre-wgpu` over `vendor/gpui-pre-wgpu`, re-apply the `Mellow patch` hunks (`git diff` of this directory against the published crate shows them), keep the header, and run the font tests in `theme/fonts_tests.rs` (its fixtures, small subsets of Noto Color Emoji and DejaVu Sans, are in `crates/mellow-desktop/tests/fixtures/fonts`). Once upstream has both, drop the directory, the `[patch.crates-io]` line and the `exclude` entry, and the waiting `prewarm_fonts` call if upstream redraws by itself.
- **Upstream**: propose to Zed (`crates/gpui_wgpu`) the background read as an option of `CosmicTextSystem::new` with a callback the platform turns into a redraw, and taking "m"-less families as fallbacks; Longbridge's snapshot follows Zed.

## Alternatives considered
- **`CosmicTextSystem::new_without_system_fonts`** in a vendored `gpui-pre-linux`: no fallback at all for emoji or other scripts, and a second vendored crate.
- **Reading the system fonts in the background and swapping in a fresh database**: every `FontId` would point at another face, and GPUI caches glyphs by `FontId`.
- **Waiting for the system fonts in `all_font_names`**: `gpui-component` calls it on the main thread during `init`, so start-up would wait again.
- **Putting the colour emoji font first in cosmic-text's own fallback order**: a third crate to vendor (cosmic-text), for the same result as the chain.
- **Keeping the weight 600 workaround** (#351, removed with this decision: `emoji_glyph_weight` and the emoji runs of `rich_text.rs`): fails in the composer's input and where a text font has a 600 face covering emoji (Fedora's `Noto Sans Symbols`).
