# 0029. Search messages with an FTS5 index inside the encrypted database

- Status: Accepted
- Date: 2026-10-30

## Context
The owner wants an "Elasticsearch-like" message search (ROADMAP item 15, decision of 2026-10-30): words found whatever their case and accents, phrases, exclusions, prefixes for type-ahead, Discord's filters (`from:`, `in:`, `has:`, dates), results ranked or newest first, highlighted, counted, with facets. It must be built into the binary, with the index inside the instance's encrypted database: the product promise is one binary and one data directory (ADR-0002), so no external search service. The index must never reveal a message to someone who cannot read it (ADR-0007, ADR-0015), must follow edits and deletions at once (deleted text must not linger, ADR-0006), and must not slow the single writer (ADR-0024).

The bundled SQLCipher of `libsqlite3-sys` 0.37 (SQLite 3.50.4) is compiled with `SQLITE_ENABLE_FTS5` (its `build.rs` sets it for every bundled build, SQLCipher included); the migration tests create and query the table, so a build without FTS5 fails them.

## Decision
- **Index.** Migration 0021 creates `messages_fts`, an **external-content** FTS5 table over `messages.content` (`content='messages'`, `content_rowid='id'`), tokenizer `unicode61 remove_diacritics 2` (case and accents ignored) and **prefix indexes of 2 and 3 characters**. Text is stored once, in `messages`; the index holds tokens only and reads the content back for highlights. FTS5's `secure-delete` option is on, so deleted and edited text leaves the index at once instead of lingering in older segments until a merge, as `secure_delete` does for the rest of the file.
- **Author index.** The migration also adds `messages (author_id, id)`: a search with `from:` and no words walks the author's messages instead of the whole server's (SQLite cannot use an index for a condition written `?3 IS NULL OR …`, so that search has its own statement).
- **Sync by triggers.** `AFTER INSERT`, `AFTER DELETE` and `AFTER UPDATE OF content` triggers on `messages` keep the index in step inside the writing transaction itself, whatever the path (cascades from a deleted channel or guild included). Pins and other updates do not touch it. The migration backfills with FTS5's `rebuild`.
- **Query language**, parsed on the server (`domain::search_query`): free words (all must match; each also matches as a word prefix, written `("w" OR "w"*)` so exact words rank above words merely starting so), `"exact phrase"`, `-excluded` word or phrase (exact), `word*` (explicit prefix), and the filters `from:username`, `mentions:username`, `in:channel` (an id, or in a server a channel name with or without `#`), `has:file|image|link|pinned`, `before:`/`after:`/`during:YYYY-MM-DD` in the searcher's time zone (`utc_offset_minutes`). Repeated `from:`, `mentions:` and `in:` mean any of them; unknown filters and invalid values are searched as words. At most 256 characters and 16 parts. A word matches as a prefix (implicitly or with `*`) only when its last token has 2 characters or more, the shortest prefix the index holds (`a*`, `a.b*` and `x.` are searched exactly: FTS5 applies `*` to the last token alone), and at most 4 prefix terms per query, excluded ones included; later words match exactly. Each prefix reads a range of the index, so this bounds the most expensive queries. User text reaches FTS5 only inside double-quoted strings with quotes doubled, and control characters become spaces (a NUL would cut the expression); a property test runs random queries through a real FTS5 table and never sees a syntax error. Text with no letter or digit (punctuation, emoji) is dropped, since the tokenizer finds no word in it.
- **Scope and permissions.** `POST /api/v1/guilds/{id}/messages/search` searches the guild's text channels where the requester holds `VIEW_CHANNEL` and `READ_MESSAGE_HISTORY`, computed by `channel_permissions` (`Guilds::channels_with_readable_history`); a non-member gets `NOT_FOUND`. `POST /api/v1/users/@me/messages/search` searches the conversations and groups the requester takes part in, as allowed by `direct_message_permissions`. The SQL only ever reads the channels of that list, so other channels cannot show in hits, counts or facets; `in:` naming a channel outside it names nothing, like an unknown one.
- **Blocked authors** are included, like in the channel: clients fold them, as they already do in history (ADR-0025). No per-hit flag: the client holds the block list, and a server flag would go stale the moment someone blocks or unblocks.
- **POST with a JSON body** (`{ q, sort, offset, limit, utc_offset_minutes }`, unknown fields refused), not GET with a query string: search text would otherwise sit in every reverse proxy's access log.
- **Results.** `sort=relevance` (default; bm25, then newest first) or `newest`; a search made of filters only is always newest first. Offset pagination, at most 25 per page and 1 000 results reachable (Discord's model: refine rather than page further). Each hit is the history page's `Message` (attachments, reactions, pictures) with **highlight ranges in UTF-16 code units** of its content, so the web client slices the string directly and no markup comes from the server; they come from FTS5's `highlight()` with control-character marks, and are dropped if the marked text is not the content. `total_count` counts up to 1 000 matches, the newest (`total_count_is_lower_bound` beyond, shown "1 000+"); `channel_facets` and `author_facets` give the 10 largest counts among those same 1 000, so a facet never exceeds the total; authors as `PublicUser`.
- **Reads** run on the reader pool; a search is four reads (page ids, counts, the page's messages, highlights) plus the usual attachment, reaction and picture reads of the page. Searches are rate limited to 30 per 30 seconds per user (`message-search:` keys), so type-ahead must be debounced. A user runs **one search at a time**: another one before the first answers is refused as `RATE_LIMITED`, and clients wait for each answer before sending the next. Searches hold at most **2 of the 4 reader connections** (a semaphore; others wait), so history reads always keep two. Interrupting a search over a time budget (SQLite's progress handler) is not done: sqlx does not expose it on pooled connections without unsafe code, and the two limits above already bound what one user can hold.
- **Deleting a channel or a guild** deletes its messages first, 1 000 per short write transaction, then the channel or guild row in its own transaction (with its audit entry, events after commit as before), from a detached task so a client hanging up cannot stop it half way. Measured below: as one cascade, the FTS5 `secure-delete` work held the writer for over a minute.
- **Reader page cache.** Each connection now keeps a **32 MiB** page cache (`cache_size`), instead of SQLite's 2 MiB: measured below, search over a database larger than the cache spends most of its time decrypting the same pages again (SQLCipher decrypts on every cache miss).

## Measurements
Release build, Apple Silicon laptop with other work running (load average 4 to 5), 50 authors, 5 servers of 20 channels, realistic messages of 3 to 24 words with French and English words, accents, links, mentions and emoji; queries searched one server (a fifth of the messages); each figure is the time for the whole search (page, counts, messages, highlights), 30 runs per query, 11 queries in both orders (`storage::search::tests::measure_search_backfill_and_latency`, `#[ignore]`d).

| Messages | Backfill (migration 0021) | Index size (messages table) | Insert, without → with the index | Search p50 / p95, 2 MiB page cache | Search p50 / p95, 32 MiB page cache |
|---|---|---|---|---|---|
| 100 000 | 0.28 s | 12.8 MiB (9.7 MiB) | 6 → 59 µs per message | 80 / 198 ms | 9.9 / 34 ms |
| 1 000 000 | 4.7 s | 118 MiB (89 MiB) | 9 → 231 µs per message | not measured | 353 / 1 073 ms |

Figures include the `messages (author_id, id)` index of the same migration (the "with" insert cost covers both indexes). That index took `from:user3` alone from 1 023 ms to 44 ms at one million messages (7.7 to 1.1 ms at 100 000).
Deleting a channel holding a fifth of one million messages, and a guild holding a tenth, with the search triggers and `secure-delete` (`storage::search::tests::measure_deletion_of_large_channels_and_guilds`, `#[ignore]`d):

| Deletion | One statement (cascade) | In batches of 1 000 | Longest wait of another write meanwhile |
|---|---|---|---|
| Channel, 200 000 messages | 68 s, writer held throughout | 66 s | 0.5 s |
| Guild, 100 000 messages | 42 s, writer held throughout | 42 s | 0.5 s |

Nearly all of it is FTS5's `secure-delete`: at 200 000 messages the same cascade took 7.2 s with it and 0.26 s without. It is kept, because deleted text must leave the file (ADR-0006); the price is that deleting a large channel or server takes a minute, during which other writes still go through.

Counting up to 10 000 matches instead of 1 000 gave 456 / 1 553 ms at one million messages, hence the 1 000 cap. The vocabulary of the generated history is small (about 120 words), so every word is common and these figures are pessimistic: a rare word costs a few milliseconds. The slowest searches at one million messages (about one second) are a very common word in one small channel (FTS5 walks every match in the instance, then keeps that channel's) and `has:link` alone, which walks the server's messages. The known remedy for the first, reading the channel's own messages instead of the index when `in:` narrows the scope to few messages, is left until a real instance needs it.

## Consequences
- Search needs nothing outside the binary and the data directory, and backups carry the index with the messages. The index takes about 1.3 times the size of the messages table, and a message insert costs 8 to 30 times more (still well under a millisecond, inside the existing transaction).
- An edit or a deletion is searchable (or gone) as soon as it commits; nothing to rebuild or resynchronise.
- Memory: up to 32 MiB per connection (one writer, four readers: 160 MiB at most, on the 2 GB target VPS), only for pages actually read. Small instances never fill it.
- The tokenizer splits on punctuation: "don't" is "don" and "t", custom emoji markup `<:party:501>` is the words "party" and "501", a link is its words. `has:link` looks for `http://` or `https://` in the text.
- Words are matched by prefix, not by edit distance: a typo inside a word finds nothing. A trigram index would find substrings and survive some typos, but it would be several times larger than the word index; it is left for later, measured first.
- Clients receive no server markup: the web client splits `content` with the ranges itself.
- Deleting a large channel or server answers only after all its messages are gone (about a minute per 200 000 messages at a million in the database); the request may outlive a proxy's timeout, the deletion still completes.
- Accepted residual risk, timing: FTS5 walks every match of a word in the instance before keeping the requester's channels, so the time a search takes grows with how often the word appears in channels the requester cannot read. Rate limits, one search at a time per user and the noise of a shared server make this a weak signal; reading the scope's own messages first when the scope is small would remove it, and is left until measured worth it.
- Accepted shortcut, daylight saving: `utc_offset_minutes` is the searcher's offset now, applied to every day of `before:`, `after:` and `during:`, so a day on the other side of a daylight saving change is shifted by an hour at its edges.

## Alternatives considered
- **An external engine (Elasticsearch, Meilisearch, Tantivy as a separate service).** Breaks the one-binary promise and keeps a second, unencrypted copy of every message.
- **Tantivy embedded in the binary.** A second store beside SQLite: its own files to encrypt, back up and keep consistent with the database after a crash, for features FTS5 already has at this scale.
- **A contentless FTS5 table.** Smaller only by not reading content back, but `highlight()` needs the content, and deletes must pass the old text anyway; external content gives both for free since `messages` already holds the text.
- **Syncing the index from the write path in Rust.** Every writer (and every cascade) would have to remember it; triggers cannot be forgotten and run in the same transaction.
- **Passing the user's text to `MATCH`.** FTS5 syntax (`NEAR`, `OR`, column filters, `^`) would leak into the query language and malformed input would fail; quoting every word keeps the language ours.
- **A cursor instead of offsets.** A bm25 cursor needs the score and id of the last hit and still re-ranks every match; offsets bounded to 1 000 results cost the same and keep the client simple.
