# 0054. Native screen sharing on the desktop

- Status: Accepted (owner's order of 2026-11-13, wave 8 of the desktop client)
- Date: 2026-11-13
- Amended: 2026-11-13 (wave 9): Windows captures through `Windows.Graphics.Capture` with an in-app picker, and its sound through WASAPI's process loopback.
- Builds on: [ADR-0051](0051-gpui-desktop-client.md) (Vesper's crates, ScreenCaptureKit, "the share's sound is captured natively"), [ADR-0052](0052-h264-next-to-vp8-in-the-voice-sfu.md) (H.264 next to VP8, a sender's codec fixed per media session), [ADR-0037](0037-screen-sharing-on-the-camera-path.md) (one video source per participant on the camera's line, the three layers, the screen's sound line)

## Context
The web client shares a screen through the browser's `getDisplayMedia`: the browser draws the picker, captures, encodes VP8 and, where the browser allows, captures the shared tab's or system's sound. The desktop client (ADR-0051) has no browser, so it captures and encodes itself, and must reach the same server checks: the camera line with the RIDs `q`, `l`, `h`, ADR-0037's sizes and rates, the voice-state flag `self_stream`, the screen-sound send line (until now empty on the desktop), and ADR-0052's H.264 rules.

What each system offers, checked on 2026-11-13:
- **macOS**: ScreenCaptureKit (macOS 12.3 and later; its audio from 13.0) captures a display or a window into `CVPixelBuffer`s in the format asked for (NV12 here), and can capture the system's or one application's sound while leaving out the capturing process's own (`excludesCurrentProcessAudio`). `SCShareableContent` lists displays and windows with their application; `SCScreenshotManager` (macOS 14) takes one picture of a source for a thumbnail. The first capture makes the system ask for the Screen Recording permission; a refusal shows as an error from `SCShareableContent`. GPUI itself runs on older macOS, so the desktop checks what the system offers at run time. `objc2-screen-capture-kit` is already in the tree through GPUI.
- **Linux, Wayland**: no client may read another's pixels. The XDG ScreenCast portal shows the compositor's own picker (screens and windows), returns a PipeWire node, and the stream delivers DMA-BUFs (GPU memory) or shared-memory pictures. Vesper's `vesper-capture` does exactly this. The portal names neither the process nor the application of a shared window.
- **Linux, X11**: any client may read the root window or a window (`GetImage`, faster through MIT-SHM) and list windows (`_NET_CLIENT_LIST`, with `_NET_WM_PID`). GPUI already brings `x11rb`. Under XWayland, X11 sees only X11 windows, never the Wayland desktop.
- **Encoders**: no common GPU encodes VP8; Linux GPUs encode H.264 through VA-API, which Vesper's `vesper-encode` drives through FFmpeg (`h264_vaapi`), but in its recording setup (B-frames, parameter sets out of band, High profile).
- **Sound on Linux**: PipeWire carries every application's playback streams; `vesper-audio` records the default output's monitor, one application's streams, or the output without some applications (it then links the other streams to itself instead of the monitor).

## Decision
### Sources and the picker
- **One trait for every system** (`mellow_media::ScreenSources`): it says which picker the system uses, lists sources for an in-app picker where the system allows it (with thumbnails when asked), and starts a capture of one chosen source. A test implementation (`SyntheticScreens`) draws a moving pattern.
- **macOS**: an **in-app picker** fed by `SCShareableContent` (displays, and on-screen windows of other applications with a title), with thumbnails from `SCScreenshotManager` on macOS 14 and later (none on 12.3 and 13). `SCContentSharingPicker` (macOS 14) is not used: the in-app picker works on every supported version and looks like the web's quality chooser around it. The capture is an `SCStream` delivering NV12 (video range) at the source's size fitted to the chosen quality, at most 30 frames per second, cursor shown. A display share leaves out every window of Mellow (`excludingApplications` with Mellow's own `SCRunningApplication`), so the call never appears in it. A refused permission is `ScreenCaptureError::PermissionDenied`, which the interface turns into a sentence pointing to System Settings.
- **Wayland**: **the portal's dialog is the picker**: the interface offers one "Share your screen" action, the compositor asks which screen or window. The restore token is **not** kept (`persist_mode` "do not"): the web client asks again at each share, so the desktop does too; a remembered source could start a share the person did not just choose. Streams come as DMA-BUFs when the H.264 path is used, else as shared memory (see Encoding).
- **X11** (the session is X11, not Wayland with XWayland): an **in-app picker** of the screens (RandR monitors) and of the managed windows (`_NET_CLIENT_LIST`, titles from `_NET_WM_NAME` or `WM_NAME`, Mellow's own windows left out by their `_NET_WM_PID`), with thumbnails taken by one `GetImage` and shrunk. Pictures are read with MIT-SHM `GetImage` into one shared segment reused for every picture (plain `GetImage` without MIT-SHM), BGRX, paced at 30 frames per second; a closed window ends the share, a minimised one repeats its last picture. A **window is read from its own off-screen picture** (Composite: `RedirectWindow` automatic, then `NameWindowPixmap` for each picture, as OBS's window source does), never from the screen where it lies: without a compositing manager (i3, bspwm, dwm without picom) the screen there shows whatever covers the window, a password manager or a private conversation the person never chose to share. An X server without Composite 0.2 offers no window, only screens. A display share on X11 cannot leave Mellow's windows out (X11 has no such filter); the panel stays visible to watchers, as in a browser sharing its own screen.
- **Windows** (10 1903 and later; older ones say the action is unavailable): an **in-app picker**, as on macOS and X11, rather than the system's `GraphicsCapturePicker`, which needs a window handle and a UI-thread asynchronous call GPUI does not give the engine, and would not leave room for the quality choice. Displays come from `EnumDisplayMonitors`; windows from `EnumWindows`, keeping those a person would switch to (visible, not cloaked by DWM, not tool windows or owned dialogs, with a title) and leaving Mellow's own out by process. Thumbnails are drawn by GDI: `StretchBlt` from the screen for a display, `PrintWindow` with `PW_RENDERFULLCONTENT` for a window (so a covered window shows whole, as X11's Composite does). The capture is a `GraphicsCaptureItem` for the monitor or window on a free-threaded `Direct3D11CaptureFramePool` (BGRA, two buffers, Direct3D 11 on the GPU or WARP without one), read 30 times a second: the newest frame is copied into one reused staging texture and from it into a recycled BGRA buffer; a resized source re-creates the pool, a closed one (the item's `Closed` event) ends the share. Windows draws its yellow capture border around the source, the system's own indicator. A **display share leaves Mellow's windows out** with `SetWindowDisplayAffinity(WDA_EXCLUDEFROMCAPTURE)` (Windows 10 2004 and later), applied to each of Mellow's top-level windows before the capture starts and again at every picture while the share runs, and undone when it stops. DWM applies it at a later composition, so pictures are held back for 100 ms after any window is newly excluded (the share's first pictures, a window opened during it): none composed before the exclusion took effect goes out. A hung window gets no thumbnail (`IsHungAppWindow`), since `PrintWindow` would wait for it forever.
- **Privacy**: nothing is captured without the person's choice made at that moment, in the in-app picker or the system's dialog; the system's own indicators stay (macOS's menu bar recording indicator, the compositor's screen-cast indicator on Wayland). The system's capture (picture and sound) stops whenever the share turns off, whatever turned it off: the interface dropping its `ScreenShare`, `stop_video`, another video source, the session leaving the channel (ADR-0037), the source closing (window closed, portal session revoked; the session then says so with `VoiceSessionEvent::ScreenShareEnded`), or the server refusing or turning the video off. A watcher thread per share checks it five times a second and stops the capture, so no indicator stays on behind a share that is off; the interface still drops its `ScreenShare` on those events, off its own thread (stopping waits for the system). On macOS a stopped stream is detached from its output and the output kept alive until the system confirms the stop, and a stream whose start answers after Mellow stopped waiting (a late answer to the permission prompt) stops itself. Logs never hold window titles or application names (Vesper's audio capture logs an application only at debug level).

### Encoding
- **H.264 on Linux with VA-API, on Wayland**: when the system's FFmpeg opens `h264_vaapi` in the profile WebRTC needs, the capture asks the portal for DMA-BUFs and the pictures stay on the GPU from capture to network (ADR-0051's purpose). `vesper-encode` gains a real-time mode for this: **Constrained Baseline** (`profile_idc` 66 with `constraint_set1`), **no B-frames**, parameter sets **in the stream** (no global header; the sender also puts the last SPS and PPS before any IDR that lacks them), one encoder per layer at ADR-0037's sizes and rates (`h` at the source fitted to the quality, `l` half, `q` a quarter, the two lower ones scaled on the GPU from the top one), constant bit rate, one picture in flight (`async_depth` 1), and an IDR on each keyframe request for its RID. Frames go out in packetisation mode 1, as `str0m` writes H.264. The offer then carries **H.264 only on the camera line** (`profile-level-id` `42e01f`, packetisation mode 1, its RTX) while every receive line stays as before (H.264 there only where the desktop decodes it, so a sharer in H.264 still receives others' H.264 shares once the call view's decoders are in): following ADR-0052, a sender's codec is fixed per media session, so starting an H.264 share **offers the session again** with that camera line (a short gap in the call's audio, as a reconnection), and a later VP8 source (the camera, a share without VA-API) offers again with VP8.
- **VP8 everywhere else**: macOS (VideoToolbox's H.264 would also need a renegotiation and was not measured against libvpx yet), Linux without a usable VA-API H.264 encoder (the portal then sends shared memory), X11 (CPU pictures), and Windows (Media Foundation's H.264 encoders are mostly hardware MFTs with an asynchronous event model, one per GPU vendor, whose Constrained Baseline and parameter-set behaviour could not be checked on any Windows machine this wave; read back to the CPU, the pictures go through libvpx as on X11): the existing VP8 simulcast path with `ScreenShareQuality`, fed through `VideoInput`, whose byte buffers are recycled so capture does not allocate a picture each frame.
- **Watchers**: a desktop that does not decode H.264 gets no slot for an H.264 share, and the voice state's `video_codec` says why (ADR-0052); browsers decode it. Decoding H.264 on the desktop belongs to the call view, whose decoders also put H.264 back on the receive lines of an H.264 sharer's offer.

### The share's sound
- Captured natively, sent as Opus (payload type 111, 48 kHz, stereo, 20 ms packets) on the **screen-sound send line**, which the server relays to watchers only while the picture is relayed (ADR-0037), exactly as the web client's.
- **macOS**: ScreenCaptureKit's own audio on the same stream (`capturesAudio`, 48 kHz stereo, `excludesCurrentProcessAudio`): a window's application only for a window, the whole system without Mellow's sounds for a display. Needs macOS 13; on 12.3 a share has no sound and says so.
- **Linux**: `vesper-audio` on PipeWire. A whole screen: the default output without Mellow's own streams (Vesper's exclusions, matched by Mellow's process binary); when the default output cannot be followed (no default metadata), the share's sound goes silent and retries rather than record the output's monitor with every application, which would send the call's own voices back to it. An X11 window: the playback streams of the window's application, matched by the binary of `_NET_WM_PID`'s process, only when the window's `WM_CLIENT_MACHINE` is this machine (a remote `ssh -X` client's process id names nothing here). A **Wayland window: no sound by itself**, because the portal names no application; the interface may offer the applications playing sound (`ScreenSources::sound_applications`) for the person to pick, the native equivalent of the web's "audio input as the share's sound".
- **Windows** (10 2004 and later): WASAPI's **process loopback** (`ActivateAudioInterfaceAsync` on `VAD\Process_Loopback`), 48 kHz stereo float. A display: every process **but Mellow's own tree** (`PROCESS_LOOPBACK_MODE_EXCLUDE_TARGET_PROCESS_TREE`), so the call's voices never go back into it. A window: its process tree only (`GetWindowThreadProcessId`), except when that tree holds Mellow: Mellow's ancestors (a terminal that started it, `explorer.exe` for anything started from Start or the taskbar, found by their parent process ids) and the shell itself, whose tree is the whole session; such a window shares no sound (`ShareSoundState::NotAvailable`), as a window of Mellow's own, rather than send every application's sound and the call's own voices. The in-app picker offers no separate application choice on Windows (a window already brings its application's sound). Older Windows versions fail the activation: the share goes on without sound and says so (`ShareSoundState::NotAvailable`).
- The sound is never mixed into the voice, has its own packets (counted in the voice budget the server doubles while sharing) and stops with the picture.

## Consequences
- The owner's Linux machine shares a 1440p screen without libvpx, from GPU to network; macOS and other Linux machines share through libvpx (one to two cores at 1440p, ADR-0051).
- Starting or ending the H.264 kind of share renegotiates the media session: a fraction of a second of silence for everyone hearing the sharer. Done only when the codec changes. Each renegotiation is a `voice_join`, counted in the server's ten joins per user a minute: switching between the camera and an H.264 share more than about five times in a minute gets the next join refused (`RateLimited`), which ends the call like any refused join.
- The Linux desktop links VA-API and FFmpeg (already the case since ADR-0051's amendment); a machine whose driver lacks Constrained Baseline encoding falls back to VP8 silently.
- Windows shares through libvpx (read back from the GPU), like X11; an H.264 path through Media Foundation is left for when it can be tried on real Windows GPUs.
- Nothing here has run on real hardware yet: the portal on KDE, GNOME and Hyprland, VA-API on AMD and Intel, ScreenCaptureKit's permission prompt and audio; each is tried before the feature is called done in the roadmap.

## Alternatives
- **`SCContentSharingPicker` on macOS 14**: the system's picker, no permission prompt beyond it, but not on 12.3 and 13 and no place for the quality choice; kept for later.
- **Keeping the portal's restore token**: shares would skip the dialog, which the web cannot do, and a share could start without a fresh choice.
- **VP8 from DMA-BUFs** (read back to the CPU): costs the copy and libvpx; shared memory from the portal does the same with less code when VA-API is missing.
- **H.264 on the macOS side with VideoToolbox**: possible later with the same renegotiation; not needed for the first release and not measured.
- **A Wayland window's sound by guessing the application** (from the window title): wrong too often; an explicit choice is honest.
- **XWayland capture on Wayland**: shows only X11 windows, never the desktop; refused.
