# 0044. Provider embeds

- Status: Accepted
- Date: 2026-11-05
- Amends: [ADR-0041](0041-link-previews-fetched-by-the-server.md) (what a preview holds, the JSON the fetcher reads, the policy's `frame-src`, the cache key)

## Context
ADR-0041 gives every link the same card: site name, title, description, one picture, and a YouTube player. Members post YouTube videos and Shorts, YouTube Music tracks, GitHub repositories and pull requests, Spotify, Deezer, SoundCloud, Apple Music and Bandcamp items, Vimeo and Twitch videos and Wikipedia articles, and the card cannot say what matters for each: a repository's stars and language, a pull request's state, a track's artist, where a video starts (owner's #roadmap, "and other sites"; the design is `docs/design/web-provider-embeds.md`). Most of these facts come from the providers' public APIs and oEmbed endpoints, which answer JSON, not HTML; and their players live on origins the page's policy does not allow. Links to the same video also differ by tracking parameters (`?si=` is per sharer), so the cache of ADR-0041 fetched each spelling again and showed the first sharer's link to every reader of the preview.

## Decision
- **A preview may carry an embed**: `LinkPreview.embed`, optional, a `LinkEmbed` told apart by `kind`: `youtube_video` (id, Short, start, playlist, duration), `youtube_music_track` (id, artist, album, duration), `github_repository` (owner, name, stars, forks, language and its colour, topics, SPDX licence, archived), `github_issue` and `github_pull_request` (owner, repository, number, state among open, draft, merged, completed, not planned and closed, author, dates, comments), `music` (provider among Spotify, Deezer, SoundCloud, Apple Music and Bandcamp, item, the provider's id, Apple Music's storefront, artist, track count, duration), `vimeo_video` (id, privacy hash), `twitch` (channel, video or clip, id) and `wikipedia_article` (language, disambiguation). The card's `title`, `description` and `image` keep the title, the summary and the one picture (cover, avatar, poster, thumbnail), through the same picture pipeline and route. The addition is optional both ways: older clients ignore the field; a kind, provider, item or state a client does not know reads as `Unknown` in Rust clients (`#[serde(other)]`), and clients show the plain card for it. Servers never send `unknown`. The web client reads `embed` only through `knownLinkEmbedOf`, which returns nothing for a kind or value it does not know, so a newer server's values never reach a layout that assumes a closed list.
- **Storage**: migration 0039 adds `link_previews.embed`, the embed's JSON, checked to be an object with a text `kind`. A stored embed this binary cannot read (written by a newer release before a rollback) is dropped when read, so the card still shows. Embeds share the preview's lifetime and purge.
- **Providers' JSON**: the fetcher reads `application/json` (and `+json` types, oEmbed's included) with the guard of ADR-0041 (public addresses, each redirect checked, 3 s to connect, 8 s per fetch, the message's 30 s budget shared by every link, page and picture), and at most 64 KiB: a longer answer is refused, since a truncated document cannot be read. Each provider slice names the API or oEmbed host it calls and records it here:
  - **YouTube** (videos, Shorts, YouTube Music tracks): `https://www.youtube.com/oembed?format=json&url=https://www.youtube.com/watch?v=<id>` for the title and the channel (a YouTube Music track's artist is its generated "Artist - Topic" channel without the suffix), and the poster at `https://i.ytimg.com/vi/<id>/maxresdefault.jpg`, else `hqdefault.jpg`, built from the checked id, never from the answer's `thumbnail_url`. The page itself, 1.4 MB and behind a consent wall from some servers, is fetched only when oEmbed does not answer (a private or removed video), as before. Duration and album are not in oEmbed and stay absent.
- **One canonical link per thing**: when a message's links are found, a link a provider recogniser understands is rewritten to one form, which is fetched, cached under and shown as the preview's `url`. Repeated links are dropped after the rewrite, so two spellings of one video take one of the message's three previews and a message never lists the same preview twice (the web client keys its cards by preview id). Today YouTube: `https://www.youtube.com/watch?v=<id>` (`/shorts/<id>` for a Short, `music.youtube.com` kept for YouTube Music) with only a public playlist and the start time in seconds; `si`, `feature`, `pp` and the like go. Other links keep their exact spelling, so their cache key is unchanged.
- **Players, after a click only**: the page's `frame-src` is the closed list `PLAYER_FRAME_ORIGINS` (`www.youtube-nocookie.com`, `open.spotify.com`, `widget.deezer.com`, `w.soundcloud.com`, `embed.music.apple.com`, `bandcamp.com`, `player.vimeo.com`, `player.twitch.tv`, `clips.twitch.tv`), written by the one function that builds the policy with or without Klipy. All are listed now, so later slices change no policy; the client creates a provider's iframe only after the reader presses play, from an address it builds out of an id it checks again with a strict pattern, never from a URL the page or the server sent. Before the press, nothing is requested from the provider: pictures come from the instance.
- **How a player is framed**: every provider iframe gets `sandbox="allow-scripts allow-same-origin allow-presentation allow-popups allow-popups-to-escape-sandbox"`, `referrerpolicy="strict-origin-when-cross-origin"` and an `allow` list by kind: `autoplay; encrypted-media; picture-in-picture; fullscreen` for a video, `autoplay; encrypted-media` for music. One player plays at a time: pressing play on another card closes the open one. Since the policy already frames every origin, these attributes are the limit on what a player can do; a slice that needs another token or permission amends this ADR. Each provider's player inside this sandbox is not verified yet; each slice tests its own.
- **No GitHub token**: GitHub's API is called without credentials (60 requests an hour per instance); a token in `mellow.toml` waits until rate limits are measured on a real instance.
- **Nothing else changes**: one fetch per thing per day, failures cached for an hour, the user agent, the logs (counts only), the queue and its two jobs, and the picture rules of ADR-0041 stay.

## Consequences
- A provider slice is a recogniser, a fetcher filling `embed`, and the client's layout; no protocol change, migration or policy change.
- The YouTube preview's `url` is the canonical link, not the poster's spelling: a reader of another channel never sees the first sharer's `si=`. Start time and playlist stay in it, so the player behaves as before. Messages that already show a preview keep it as stored; the next post of the link fetches it under the canonical form.
- The policy frames nine origins where one was used; frames are still created only by the web client's own scripts, after a press, and `frame-ancestors 'none'` still keeps the client out of other pages' frames.
- A JSON answer is parsed on the async thread, unlike a page: `serde_json` is linear and the body is at most 64 KiB, a sixteenth of a page's limit (not measured).

## Alternatives considered
- **Each player origin added to `frame-src` when its slice ships** (the design note's first wish): one more policy change and security review per slice for no gain, since no script of ours frames an origin before its slice.
- **A second picture per preview** (a poster and a cover): no kind needs two; the design keeps one picture.
- **Embed fields flattened into `LinkPreview`**: dozens of optional fields with no rule saying which go together; a tagged union says it.
- **Cache keys like `youtube:<id>`** without rewriting the stored link: the first sharer's link, tracking id included, would be shown to everyone linking the same video.
