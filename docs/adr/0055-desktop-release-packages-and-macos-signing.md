# 0055. Desktop release packages, a stable self-signed macOS identity and the system's FFmpeg

- Status: Accepted (owner's decision of 2026-11-13, wave 9 of the desktop client)
- Date: 2026-11-13
- Builds on: [ADR-0016](0016-sign-releases-in-a-protected-ci-environment.md) (signing in the `release` environment), [ADR-0051](0051-gpui-desktop-client.md) (the desktop client)
- Supersedes: the "Packaging" point of ADR-0051's FFmpeg amendment (a pinned FFmpeg linked statically into the Linux release)

## Context
The desktop app (ADR-0051) is built only from source so far. Step 9 ships it: a macOS app and a Linux package, made by the release workflow from a tag and signed like the server's binaries so the desktop's self-update can verify them.

On macOS, an executable outside a bundle has no `Info.plist`, so the camera, microphone and Screen Recording prompts go to whatever launched it, and notifications have no bundle to belong to. Privacy permissions (TCC) are remembered per code identity: for a signed app, its designated requirement, which names the signing certificate; for an ad hoc signature, the hash of that very build, so every update asks again. Apple's own answer, a Developer ID certificate plus notarisation, needs the paid Apple Developer Program (99 USD a year) and Apple's notary service for every release.

On Linux, the desktop calls FFmpeg's C API (`libavcodec`, `libavfilter`, `libavutil`) for Vesper's VA-API encoder, the camera's MJPEG decoder and H.264 decoding (ADR-0051's amendment, ADR-0054). ADR-0051 planned a minimal FFmpeg built from source and linked statically, so one tarball would run everywhere. The owner decided on 2026-11-13 to rely on the system's FFmpeg instead: the distribution's build is the one its VA-API drivers are tested with, it gets the distribution's security fixes, and Mellow builds and audits no media C library of its own. FFmpeg's shared libraries carry their major version in their file name (`libavcodec.so.60` for FFmpeg 6, `.61` for 7, `.62` for 8, and so on), and the structures Mellow reads change between majors, so one binary runs only where its major is installed. On 2026-11-13 (Repology): Ubuntu 24.04 ships FFmpeg 6.1; Debian 13, Fedora 42 and 43, Ubuntu 25.04 and 25.10 ship 7.1; Ubuntu 26.04 and Fedora 44 ship 8; Arch Linux (and CachyOS, the owner's system) ships 9. Ubuntu 22.04 (4.4) and Debian 12 (5.1) are older than the 6.1 Mellow builds against.

## Decision
### macOS
- **A `Mellow.app` bundle**, laid out by `cargo xtask macos-app` from `crates/mellow-desktop/packaging/macos`: `Info.plist` (bundle identifier `org.mellow.desktop`, the desktop's `APP_IDENTIFIER`; the workspace version; minimum macOS 11.0, Rust's floor for Apple silicon, with `MACOSX_DEPLOYMENT_TARGET=11.0`; camera and microphone usage sentences in English and French; category Social Networking; high resolution), `Mellow.icns` rendered from the generated favicon on Apple's icon grid (824 of 1024 points), and the hardened runtime's entitlements: camera and audio input only. Screen Recording has no entitlement and no usage string (macOS words that prompt itself). No JIT, unsigned executable memory or library validation exception: GPUI's Metal shaders compile in Apple's own service and the binary loads no library of its own.
- **Signed with a stable self-signed code-signing certificate** ("Mellow Desktop", RSA 3072, 100 years, made once by `packaging/macos/make-signing-certificate.sh`). Its designated requirement pins that certificate, so TCC keeps the camera, microphone and Screen Recording permissions across updates. Gatekeeper does not trust it: the first launch is blocked, and the user opens the app once through System Settings → Privacy & Security → "Open Anyway" (README). No secure timestamp: Apple's service only vouches for Apple-issued certificates.
- **Where the key lives**: like the minisign key (ADR-0016), only in the GitHub environment `release`, as `MACOS_SIGNING_CERTIFICATE` (the PKCS#12, base64) and `MACOS_SIGNING_CERTIFICATE_PASSWORD`, never in the repository. The maintainer keeps one offline copy (a password manager) to recover from a lost secret. The job `desktop-macos-sign` imports it into a temporary keychain with a random password, signs, and deletes the keychain on exit (`packaging/macos/sign-app.sh`); it runs no code built in the workflow while the identity is present. It is the second job waiting for the maintainer's approval in a release run, after the build jobs and before `publish`.
- **One universal app**: `aarch64-apple-darwin` and `x86_64-apple-darwin` are built natively on an Apple silicon and an Intel runner, then joined by `lipo`. One download for every Mac, and the self-update has no architecture to pick; the cost is a second macOS build per release and a binary about twice as large.
- **A `.zip` (made by `ditto`)**, not a `.dmg`: the same file installs (Safari unpacks it; the user moves `Mellow.app` to Applications) and updates (unpacked by the self-update without mounting a disk image), and `ditto` keeps the signature and modes. A `.dmg` would add a mount step to the update path for a nicer first install only.
- Pull requests that change the packaging run the whole path with a throwaway certificate made on the runner, without the environment.

### Linux
- **A tarball per FFmpeg major version**, each built in a container of the oldest maintained distribution shipping that version, so its glibc is the oldest of the group: FFmpeg 6 on Ubuntu 24.04, 7 on Debian 13, 8 on Ubuntu 26.04, 9 on the day's Arch Linux (rolling distributions follow Arch's glibc). `x86_64` only for now. Assets: `mellow-desktop-X.Y.Z-x86_64-unknown-linux-gnu-ffmpegN.tar.gz`. A new FFmpeg major in a supported distribution adds a matrix line; one that leaves every maintained distribution drops one.
- **Contents** (`cargo xtask linux-package`): `bin/mellow` (stripped), `share/applications/mellow.desktop` (named after the window's Wayland `app_id`), `share/icons/hicolor` (PNGs from 16 to 512 pixels and the SVG), `share/metainfo/org.mellow.desktop.metainfo.xml` (AppStream asks for a reverse-DNS id, the bundle identifier), `LICENSE` and `install.sh`, which installs into `~/.local/bin` and `${XDG_DATA_HOME:-~/.local/share}` without root, writes the binary's full path into the desktop entry, replaces a running binary by renaming, refuses with the missing library names when `ldd` finds one (pointing at the package for another FFmpeg), and removes everything with `--uninstall`.
- **Runtime dependencies are the system's**: FFmpeg's libraries, libva and the GPU's VA-API driver, PipeWire, ALSA, xkbcommon, Wayland or X11, Vulkan, fontconfig and FreeType, the XDG desktop portal, a Secret Service. The packages per distribution are listed in the README. The app already probes at run time for FFmpeg's H.264 decoder and the `h264_vaapi` encoder and falls back to VP8 when either is missing (Fedora's `ffmpeg-free` and its Mesa without H.264 encoding, for instance); the FFmpeg libraries themselves are a hard dependency. Building against the system's FFmpeg stays the only way, for releases, development and CI alike.
- The release job checks that the container's FFmpeg is the expected major, that `ldd` resolves every library and lists `libavcodec`, validates the desktop entry and the metainfo, and runs the installer into a throwaway home and back out.

### Both
- The archives are signed like the server's binaries: one `.minisig` per asset whose trusted comment is the asset's name, and every asset in `mellow-X.Y.Z-SHA256SUMS`, signed too (ADR-0016). The `publish` job refuses a release whose asset list differs from the expected one.
- Windows has no package yet: its build is checked in CI only; a zip or an MSI, and its own signing question, come with the Windows work.

## Consequences
- Updates keep macOS permissions as long as the certificate stays the same. **Changing the certificate** (lost key, compromise) resets every user's camera, microphone and Screen Recording permissions and shows Gatekeeper's first-launch block again. Rotation: make a new identity with the script, replace both secrets, release, and say so in the release notes. A compromised key lets its holder sign apps macOS treats as Mellow for TCC, so it is rotated at once; the minisign signature still guards updates, since the self-update checks it before installing anything.
- Every user meets Gatekeeper's block once per installation, and macOS does not show the developer's name. Moving to Developer ID later is a new certificate, so it resets permissions once.
- Four Linux builds per release, about as long each as a desktop CI build, and a release workflow that must follow FFmpeg majors. A distribution upgrade to a new FFmpeg major leaves an installed Mellow unable to start until the user installs the matching package (the self-update picks it by the system's libavcodec, the `install.sh` message says which).
- Fedora users need RPM Fusion's FFmpeg and Mesa drivers for H.264 (README); without them calls stay on VP8.
- Releases need the two macOS secrets in the `release` environment before the first tag that builds the desktop; without them the macOS signing job fails and nothing is published.

## Alternatives
- **Developer ID and notarisation**: no Gatekeeper block and a named developer, but a paid yearly membership, an Apple account bound to the project and Apple's notary in every release. Rejected by the owner for now; possible later at the cost of one permission reset.
- **Ad hoc signatures only**: free and no secret, but TCC would forget the camera, microphone and Screen Recording permissions at every update, the problem this decision exists to solve.
- **A `.dmg`**: a drag-to-Applications window on first install, at the cost of mounting it in the update path. Can be added beside the zip later without changing the update.
- **Per-architecture macOS apps**: cheaper releases, but two downloads to choose between and an architecture choice in the self-update.
- **FFmpeg linked statically from a pinned source build** (ADR-0051's plan): one Linux tarball for every distribution, at the cost of building and patching FFmpeg ourselves and carrying codec and driver compatibility the distributions already handle. Replaced by the owner's decision.
- **Loading FFmpeg at run time (`dlopen`) whatever its version**: one tarball, and the app would start without FFmpeg. It needs bindings per major version for every structure read, which `rusty_ffmpeg` does not offer; kept as a later option if the number of FFmpeg majors in use grows.
- **Flatpak or AppImage**: Flatpak brings its own FFmpeg runtime and sandbox portals but needs a Flathub submission and manifest upkeep; AppImage would bundle libraries again. Possible later, beside the tarball.
