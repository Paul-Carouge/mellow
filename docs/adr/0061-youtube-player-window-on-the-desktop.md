# 0061. YouTube videos play in a Mellow player window on the desktop

- Status: Accepted
- Date: 2026-11-14
- Builds on: [ADR-0041](0041-link-previews-fetched-by-the-server.md) (players in `youtube-nocookie.com/embed`), [ADR-0051](0051-gpui-desktop-client.md) (GPUI desktop client), [ADR-0055](0055-desktop-release-packages-and-macos-signing.md) and [ADR-0060](0060-windows-release-package.md) (the packages), [ADR-0057](0057-desktop-self-update.md) (self-update)

## Context
On the web, a YouTube card plays the video in place, in YouTube's privacy-enhanced embedded player (ADR-0041). The desktop app's card opened the link in the browser: the owner wants the video to play from the app itself. GPUI draws no web content, and YouTube's terms require its own visible player (no extracted stream). The owner chose, among three options (a player window, a web view inside the main window, the browser), a **Mellow player window**: a floating window in Mellow's colours, resizable, that can stay on top, holding YouTube's official player; nothing opens in the browser.

## Decision
- **A process of its own, `mellow-player`**, a second binary of the new crate `crates/mellow-player`, installed beside `mellow` (Linux `~/.local/bin`, `Mellow.app/Contents/MacOS`, `%LOCALAPPDATA%\Programs\Mellow`). It runs its own tao event loop and a wry web view: WebKitGTK 4.1 on Linux (X11 and Wayland, through GTK), WebView2 on Windows, WKWebView on macOS.
  - The app links no web engine: a missing WebKitGTK cannot stop Mellow from starting, and the window's process holds no session token. The release workflow checks with `ldd` that `mellow` does not link `webkit2gtk`.
  - **Separate is not sandboxed**: the window runs as the same user as Mellow, so a hole in the web engine's renderer could read what that user can, Mellow's stored session included. The web content itself therefore runs in the engine's sandbox: on Linux the app starts the window with `WEBKIT_FORCE_SANDBOX=1`, and WebKitGTK runs its content processes in bubblewrap (`bwrap`, own user, mount and network namespaces, no home folder) with `xdg-dbus-proxy` filtering D-Bus; checked on CachyOS with WebKitGTK 2.54.2 (the content process's user namespace differs from the window's). If the sandbox cannot start, WebKitGTK ends the window, and the app falls back to the browser (below). WebView2 and WKWebView sandbox their content processes themselves.
  - The crate's library is the pure part both processes share (the messages, the validation, the navigation filter, the window's placement); its binary, which uses tao and wry, builds only with the crate's `window` feature, which the app never turns on: `mellow-desktop` neither builds nor links GTK or WebKitGTK, and building it needs no `libwebkit2gtk-4.1-dev`.
- **Protocol**: the app starts `mellow-player --data-directory <dir> --background #rrggbb [--placement WxH[@X,Y]] [--keep-on-top]`, then writes one JSON command per line on its standard input (`play`, `keep-on-top`, `close`) and reads one JSON event per line from its standard output (`ready`, `playing`, `keep-on-top`, `open-in-browser`, `unavailable`, `closed` with the window's placement). Lines are bounded (16 KiB) on both sides: a longer line is skipped to its end in buffer-sized steps, never held whole nor read again as a new line; unknown lines are ignored. The window writes its events on a private, close-on-exec copy of its standard output and points its standard output at its standard error, so the web engine's processes, which inherit the standard descriptors, cannot write the protocol. The app opens at most one YouTube page per second in the browser and checks a placement it receives like a stored one. **The end of the standard input is the end of the app**: the window closes, so it never outlives Mellow, killed or crashed; the app reaps the process from a thread waiting on it, and its exit code (3: no web view, 4: the web view failed, or death by a signal) also sends the video to the browser when the window's last events were lost. When Mellow quits with the window open, it sends `close` and waits 100 ms at most for `closed`, to save where the window was.
- **What the web view may load**:
  - only `https://www.youtube-nocookie.com/embed/<id>?autoplay=1[&start=N][&list=L]`; the video id is checked (`[A-Za-z0-9_-]{11}`), the playlist (10 to 64 of those characters, not a viewer's `RD…` mix), the start (above zero), by the app and again by the window before it builds the address;
  - every navigation of the page goes through the filter (on Linux and macOS every frame's; on Windows only the top document's, since the WebView2 event wry follows, `NavigationStarting`, is the main frame's: a frame inside YouTube's page loads there what that page asks, still in the browser engine's sandbox): the player's address on HTTPS, port 443, no credentials, and the empty frames `about:blank` and `about:srcdoc` pass; a YouTube page (`youtube.com`, `www.`, `m.`, `music.`, `youtu.be`, HTTPS only) is handed to the app, which checks it again and opens it in the system browser; anything else is blocked. New windows are always refused (a YouTube link among them goes to the browser);
  - incognito (no cookie or storage outlives the window, none shared with the browser or the app), downloads refused, every permission request denied, developer tools off, zoom keys off, no IPC handler and no initialisation script: the page has no channel to the native side;
  - the web view's folder is `<local data>/mellow[-<profile>]/player-web-view` (`MELLOW_PROFILE` respected). Incognito keeps the page's cookies and storage in memory; the engines still write their own files there: WebView2 its runtime's profile, WebKitGTK empty cache folders, salts and an empty HSTS database (checked: no site in it). The Windows uninstaller removes the folder.
  - **Referrer**: YouTube's embedded player refuses to play without one (its error 153) and asks apps to name themselves by their identifier as an HTTPS origin. The window sends `Referer: https://org.mellow.desktop/` with the player's address, the identifier of the macOS bundle and Linux desktop entry; never the instance's address.
- **Behaviour**: one window at most. A click on another video plays it there and brings the window to the front. A second click on the video it shows (or a double click) only brings it forward, without starting over. The title is the linked page's title (control characters, zero-width characters and direction marks, embeddings, overrides and isolates removed, 200 characters at most); the icon is Mellow's; the window and the web view are painted in the theme's player background (`component.link-preview.player-background`, Dusk) before the player draws; the window opens 16:9 for a video, 9:16 for a Short. Its size and position are kept in the preferences (`youtube-player-window`), not when it closes maximised, minimised or full screen; it reopens there when at least 48 × 48 pixels of it fall on a connected screen, its size cut to that screen. **Keep on top** (`youtube-player-on-top`) is toggled by Ctrl+T (⌘T on macOS) in the window, or by the app. Escape closes the window, except while the player is full screen, where it leaves full screen (WebKitGTK's `enter-fullscreen` and `leave-fullscreen` tell; on Windows the window follows WebView2's `ContainsFullScreenElementChanged`, whose full screen otherwise only fills the web view; macOS has neither, and the window filling its screen stands for it). On Windows these keys reach WebView2's own window, so its `AcceleratorKeyPressed` event hands them over, a key held down only once; WebKitGTK hands an unhandled key back to the window a second time, so a repeat within 150 ms is ignored.
- **The app's side** (`mellow-desktop/src/youtube_player.rs`): a GPUI global tracks whether the window is starting or open, which video it shows, its keep-on-top state and the last video it failed to open. The YouTube card asks `youtube_player_video` and shows "Playing in the player window" on its picture while the window shows its video (a plain chip until the card design track dresses it), and `youtube_player_fallback`; `set_youtube_player_keep_on_top` and `close_youtube_player` act on the window. Every change redraws the windows.
- **When the window cannot play, the browser opens the video, and the card says so** ("The player window couldn't open, so the video opened in your browser."): no `mellow-player` beside the app, WebKitGTK missing (the process ends before `ready`), WebView2's runtime missing (`unavailable`), WebKitGTK's content process ending, which it does when GStreamer's base and good plugins are missing (`unavailable`), or WebKitGTK's sandbox not starting (the window aborts; seen with D-Bus unreachable). Never a crash of the app.
- **Packages**:
  - Linux: the tarball carries `bin/mellow-player`; `install.sh` installs and removes it, and says, without refusing, when WebKitGTK 4.1, GStreamer's plugins (`gst-inspect-1.0`, then the usual folders), `bwrap` or `xdg-dbus-proxy` are missing and which packages to install. The release builds pass `--features mellow-player/window` and need `libwebkit2gtk-4.1-dev` (apt) or `webkit2gtk-4.1` (pacman); so do the CI jobs that lint and test the window.
  - macOS: both architectures of `mellow-player` are joined like `mellow` and put in `Contents/MacOS`; `sign-app.sh` and `cargo xtask macos-app` sign it first, with the hardened runtime and no entitlements, and the bundle's signature seals it (`codesign --verify --deep --strict`).
  - Windows: the Inno Setup script installs `mellow-player.exe`, stops a running one (by its path) with Mellow before installing or uninstalling, and its uninstaller removes it and `%LOCALAPPDATA%\mellow\player-web-view`. WebView2 is part of Windows 10 (since 2021's updates) and 11.
  - Self-update needs nothing more: Linux runs the new package's `install.sh`, macOS swaps the whole bundle, Windows runs the new installer once the app (and with it the window) has quit.

## Consequences
- Videos play beside the conversation, in YouTube's own player and under its privacy-enhanced domain, as on the web. YouTube sees the reader's address and the `org.mellow.desktop` referrer, never the instance; nothing is stored between windows.
- **Linux gains a runtime dependency**: WebKitGTK 4.1, `bwrap` and `xdg-dbus-proxy` for its sandbox, and, for its video, GStreamer's base and good plugins (and `gst-libav` for H.264). Most desktops have them (GNOME's apps use them); a minimal system without them keeps the previous behaviour, the browser, with a note on the card and at install time.
- New crates, all already used by Tauri and audited by `cargo deny`: `tao` 0.37 and `wry` 0.57 (Apache-2.0 or MIT, without their D-Bus, X11-only and developer-tools features), `webkit2gtk` 2.0 (MIT, pinned by wry; for its content-process signal), and on Windows `webview2-com` 0.39 and `windows` 0.62 (already in the tree). On Linux they bring GTK 3's Rust bindings (gtk-rs 0.18), unmaintained since GTK 3's bindings were archived, and glib 0.18, whose `VariantStrIter` advisory (RUSTSEC-2024-0429) is ignored in `deny.toml` with its reason: the window builds no GVariant. They go when wry moves to GTK 4.
- The packages grow by the player binary: 2.1 MB stripped on Linux (release build, measured), as it links the system web engine.
- The window is a second process: about the memory of one browser tab while it is open, nothing when it is closed. Its standard error goes where the app's goes (the terminal it runs in, or the system journal); it holds no title nor address.
- macOS: the window runs from inside the bundle, but as its own process; the Dock may show it beside Mellow. Not tried on a Mac yet, nor on Windows (both build in CI).

## Alternatives
- **A web view inside the main window (wry as a child of the GPUI window)**: wry cannot attach to a foreign window on Wayland (it needs a GTK container), and GPUI's window is not one; on X11, Windows and macOS it would overlay a native view on GPUI's surface, with clipping, focus and z-order bugs over the message list, and the web engine would run in the process holding the session.
- **`mellow --youtube-player` (the same binary in a second mode)**: no second file in the packages, but the app would link WebKitGTK on Linux and could not start without it; linking WebKitGTK lazily (`dlopen` of `libwebkit2gtk-4.1.so.0` and its GTK and libsoup dependencies) means hand-written bindings for the part of WebKitGTK wry uses, or patching webkit2gtk-sys, for a guarantee a separate executable gives for free.
- **Servo** (embedded through `libservo`): a full engine compiled into Mellow (hundreds of crates, a much longer build, tens of MB), whose media stack is incomplete; YouTube's player (Media Source Extensions, codecs) is not a page Servo plays reliably yet.
- **CEF** (Chromium Embedded Framework, through `cef-rs`): YouTube plays perfectly, but it ships about 100 MB of Chromium per platform and per package, needs its own update cadence for security fixes, and a sandbox and helper processes to package on three systems: against Mellow's light packages.
- **Extracting the stream** (yt-dlp and Mellow's own video decoder): plays without YouTube's visible player, which YouTube's terms forbid (ADR-0041 already rejected it), and breaks whenever YouTube changes.
- **Keep opening the browser**: what the owner asked to replace.
