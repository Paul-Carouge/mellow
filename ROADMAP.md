# Mellow — Roadmap

Each milestone ends with something usable end to end. Scope changes are made here first.

## Status (2026-11-02)

**Current focus: the web client only** (owner's decisions, 2026-10-22 and 2026-11-02, [ADR-0036](docs/adr/0036-web-client-only-and-native-clients-later.md)). Until the web client is finished, all new features, UI work and fixes target `web/` and the server and protocol it needs. The Slint desktop app was removed on 2026-11-02 (it stays in the git history); native desktop and mobile clients come back once the web is done, with their own ADR (the owner is considering Rust with GPUI), built on `mellow-client-core`. Reason: building every feature twice halved the pace.

### Known gaps and debts
- Optimisation pass leftovers: previews do not count in the uploader's quota; custom emoji are not recompressed (their id is their file's id); attachments uploaded before migration 26 have no dimensions; animated PNGs are stored as sent; the startup `currentUser` and gateway connection still run one after the other.
- Server: writes go through one connection (ARCHITECTURE §4.3) but are not batched into shared transactions; message sends are also serialized by a per-process lock (so a second process such as `admin` writing messages would not be ordered); nonces are deduplicated forever per channel and author, not for a time window, and a deleted message frees its nonce (an outbox retry after the sender deleted it recreates it); the database pool keeps sqlx's 30 s acquire timeout and history reads have no rate limit, so a read flood also queues sends behind the send lock; `messages.author_id` has no `ON DELETE` rule, to settle with account deletion (its index came with search, migration 0021); queries are runtime SQL, not compile-time checked (`sqlx` offline data to set up); member list capped at 1 000 instead of paginated; rate limits in memory, per process, and the shared table fails closed when saturated; Windows refused until the master key file gets a protected DACL.
- TLS: the ACME path is covered by one end-to-end test against Pebble (ignored by default, run in CI on Linux; renewal and the staging/production switch are not covered); certificate and account keys are protected by file permissions only, not encrypted with the master key; no HSTS header yet (no web pages served until the admin UI); connection caps and timeouts apply to the built-in TLS listener only, not to the plain HTTP one behind a proxy; slow request bodies are bounded by the 75 s idle limit per byte, not by a total deadline.
- Gateway: no per-IP cap on concurrent connections (only an opening rate and a global cap); `GUILD_CREATE` after joining does not list who is already online; the per-guild permission snapshot cache is never evicted (one entry per guild used since start) and the first restricted send after a member or role change reloads it (about 1.6 ms for 1 000 members); a slow reader's outgoing queue holds its own copy of each frame (up to about 17 MB per session, not measured); presence: a user whose cut-off session is not yet unregistered when they reconnect is never announced online; the 10 s identify timeout and the global connection cap are not covered by tests.
- Client core: the outbox lives in memory only (unsent messages are lost when the app quits); failed messages are resent automatically after each reconnect, so one the sender deleted from another device before its lost answer is recreated (a deleted message frees its nonce); order holds only inside a resend batch (a message typed meanwhile, or one that failed after the batch started, can land before older ones); a batch stopped by a failure waits for the next reconnect or a manual retry (no timer); a refused message whose text cannot go back to the composer (not empty, or another channel shown) stays failed and is refused again at each reconnect until discarded; a message confirmed by the gateway before its REST answer shows twice for that moment (the gateway event carries no nonce), and stays twice if that answer then fails; "Not sent." after a lost answer can be wrong, and its Delete only hides the message locally while the server kept it (to word as "couldn't confirm" once failures are told apart in the UI); a send the instance refuses (invalid text, missing permission, deleted reply target) goes back to the composer with the reason; no message cache on disk; older history loads when the list nears its top, with known limits: the list keeps its distance to the bottom after a page loads until the next scroll (a message arriving meanwhile shifts the view by its height), a channel left open keeps every page it loaded plus new messages (trimmed back to 500 when left), a page whose answer no longer joins the cache (reconnect, trim, oldest message deleted) is dropped and asked again at the next scroll or list change, and every incoming message rebuilds all rows of a deeply scrolled channel (not measured); unread markers only know cached messages, so after launch no channel shows unread until a message arrives (needs a `last_message_id` per channel in the protocol); a member join or leave racing the first member-list fetch is lost until the next `Ready`; `RestClient` sign-in methods take `&mut self`, which UniFFI cannot export, so the token must move behind interior mutability before `mellow-ffi` (M3).
- M0 leftovers: the admin CSS token generator.
- Roles: every new role starts lowest (position 1) until reordered; a role holding a permission a manager lacks is out of their reach whatever its position; deleting or taking away a role is not checked against a concurrent permission change of that role, and a reordering in flight still goes through, within the manager's former rank, if their role or `MANAGE_ROLES` is taken away meanwhile (nuisance only, no privilege gained; the order itself is guarded).
- Overwrites: categories do not pass their overwrites to their channels (each channel has its own, no Discord-style sync); a member's overwrite stays after they leave, as on Discord.
- Server dialogs: every "Invite people" creates a new invite that never expires and has no use limit; only text channels at the top level can be created (no categories, no topic).
- Moderation: kicks and bans keep the member's messages (no "delete recent messages" option); the ban list is capped at 1 000, not paginated; a kick or ban racing a role change of its target is decided on the ranks read before the write. A ban answers 404 for an unknown user id, so a guild owner can tell whether an id belongs to an account (ids are not guessable at the rate limit); bans per guild have no quota yet. The audit log keeps entries forever (no retention period yet), and a repeated ban of an already banned user records a new entry; every invite created by any member is recorded, which can crowd the log of a busy server.
- Web client: a late edit answer can undo a newer pin carrying the same `edited_at`; member events that arrive while the member list loads are lost until the next `Ready`; mounting a long history is still linear (about 0.2 ms per row; virtualisation or trimming the open channel would fix it); a sign-in flood from about 170 addresses can still block new sign-ins for 15 minutes (ARCHITECTURE §4.7).
- Web channel settings: text channels only (categories have no settings page, so their overwrites are not editable on the web), no "Delete channel" yet, the channel's welcome hero and the quick switcher still show `#` instead of its icon; a WebP picture carrying an EXIF orientation may be shown turned by the browser but cut unturned by the instance, which applies the orientation to JPEG and PNG only (not tried).
- Web server settings: no Members tab on a role, no drag-and-drop reordering, presets only for colours, no preview on the other theme; invites made there never expire and have no use limit; deleting a server is one cascade in one transaction (fine for community sizes, not measured on a server with a very long history) and asks for no password, only the typed server name (Discord parity, owner's decision 2026-10-22).
